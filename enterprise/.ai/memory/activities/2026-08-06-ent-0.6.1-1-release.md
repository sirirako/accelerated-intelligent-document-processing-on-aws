# 2026-08-06: Enterprise release 0.6.1-ent.1 (prerelease, for customer config-pipeline testing)

First tagged enterprise release. Upstream base 0.6.1, enterprise iteration 1.
Tag `enterprise-v0.6.1-ent.1`. Purpose: hand the customer a build to test the
document configuration promotion pipeline in their air-gapped environment,
independent of the completion-hook/broker work (still blocked on a broker SG).

## What shipped

### Config promotion pipeline (the reason for this prerelease)
- `enterprise/config-pipeline/` deploys and runs end-to-end. Validated in the
  test account (549366490058): deployed `idp-config-pipeline`, promoted a config
  into the target stack's ConfigurationTable, confirmed version semantics
  (new version inactive, active config untouched).
- Fixed a buildspec YAML bug: install-phase commands with unquoted `": "` in
  `echo "FATAL: ..."` parsed as mappings, so CodeBuild rejected the whole
  buildspec at DOWNLOAD_SOURCE ("found subkeys instead"). Every run failed
  before executing anything. Single-quoted the commands. (`8262cc46`)
- Deploying the stack does NOT surface this — only a run does. First real run is
  the test.

### Enterprise CD deployment script
- `enterprise/sdlc/codebuild_deployment.py` now passes every parameter present
  in pipeline-config, empty values included, so `Key: ""` can clear a stack
  parameter. The old `if v` filter silently dropped empties, making it
  impossible to blank a parameter (e.g. `PermissionsBoundaryArn: ""`) once set,
  and discarded legitimate `"0"`/`"false"`. (`8b0eb1b1`)

### CloudFormation service role
- Granted `iam:PutRolePermissionsBoundary` / `iam:DeleteRolePermissionsBoundary`
  in `IDP-Cloudformation-Service-Role.yaml`. Without them, updating a
  boundary-enabled stack fails AccessDenied on every stack-created role, and the
  rollback fails identically → `UPDATE_ROLLBACK_FAILED`. Customer's
  pre-deployed `aidp-cfn-service-role` needs the same two actions before its next
  boundary-enabled update; redeploying our template does NOT reach it.

### Completion hook port default
- Default MQ port corrected `61617` → `61614` across template, hook, env
  examples, and test script. The hook speaks STOMP (stomp.py); 61617 is
  OpenWire (which stomp.py can't speak), 61614 is STOMP+SSL. (`cd42b7d9`)
- Broker status: probe from inside the customer VPC shows 61617 open, 61614
  timing out (not refused) — a security-group gap, not a missing connector
  (managed Amazon MQ can't disable connectors). Customer asked to open inbound
  TCP 61614 on the broker SG from the Lambda SG. Until then the hook stays OFF
  in the customer config. See `skills/completion-hook.md`.

### Enterprise versioning
- Added `enterprise/VERSION` (`0.6.1-ent.1`), separate from the root `VERSION`
  (upstream clock). Scheme in `decisions.md`; release workflow in
  `skills/release.md`; upstream-sync checklist rolls the base on merge.

## Customer deploy note
- Customer uses their own `local-mf-aidp.yaml` (gitignored). For this prerelease
  it still has `EnableCompletionHook: "true"` and port `61617`. Customer is
  updating their config themselves: set the hook OFF (or port 61614) until the
  SG opens and `test_activemq.py --port 61614` passes.

## Not in this release / still open
- Completion hook end-to-end (blocked on broker SG for 61614).
- `WAFAllowedIPv4Ranges: 0.0.0.0/0` in the customer config — fine for private
  VPC test, tighten before real production.
